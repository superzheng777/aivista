## 1. 目标、前提与一致性边界

### 1.1 优化目标

把点赞请求主链路从“MySQL 同步事务”调整为“Redis 原子更新”，降低热门图片、热门作者记录的 MySQL 行锁竞争，并保持前端即时反馈。RabbitMQ 负责让 MySQL 和通知系统尽快跟进，定时全量校正负责最终兜底。

### 1.2 已接受的部署前提

- 后端、Redis、RabbitMQ、MySQL 均按单机环境设计，当前不处理分布式时钟、Redis Cluster 跨 slot、跨机容灾和多活问题。
- MySQL 是图片发布状态与当前公开版本的事实源；Redis 是当前有效公开周期内点赞关系与图片点赞计数的实时事实源，MySQL 同时保存这些点赞数据的最终一致副本和查询投影。
- Redis 开启本机持久化，计划使用 AOF `everysec` 并保留 RDB 辅助恢复；接受异常情况下最近短时间数据丢失，不在本方案中设计异地备份。
- RabbitMQ 是快速同步通道，不是点赞正确性的唯一保障。允许极少量消息遗漏，由定时全量校正修复点赞关系和计数。
- 系统提供最终一致性，不承诺 Redis 与 MySQL 在任意时刻始终一致。
- SSE 是尽力而为的在线通知通道，不承诺浏览器必达。

### 1.3 不引入的设计

当前方案明确不引入：

- Redis Stream；
- Redis pending outbox；
- 点赞请求中的 MySQL transactional outbox；
- 独立 `operationSequence`；
- HTTP 主链路等待 RabbitMQ Publisher Confirm；
- Redis 中独立的取消点赞记录；
- 为分布式部署预先引入的复杂顺序协议。

这些设计未来可以根据容量、丢失率和故障演练结果重新评估，但不进入第一版实现。

## 2. 当前代码事实

当前点赞系统仍以 MySQL 为事实源，尚未完成本文改造：

1. `PUT /api/inspirations/{imageId}/like?publicationVersion={version}` 确保点赞，`DELETE` 确保取消点赞，成功返回 `204 No Content`。
2. `generation_image_likes(user_id, image_id, publication_version, liked_at)` 只保存当前有效点赞关系；取消点赞时直接删除关系。
3. `generation_images.like_count` 保存图片点赞数，`users.received_like_count` 保存作者获赞总数。
4. 当前一次有效状态变化会在同一 MySQL 事务中更新关系、图片计数、作者计数、搜索 Outbox，并按规则创建互动通知及通知 Outbox。
5. `publicationVersion` 隔离同一图片的不同公开周期；撤销发布会清理当前公开周期点赞并校正计数。
6. 当前点赞限流是 JVM 内存令牌桶，不是 Redis 限流。
7. 项目现有 RabbitMQ 生成任务队列已经使用 durable quorum queue，并配置 correlated publisher confirm；这不表示点赞链路已经接入 MQ。

现有实现的优点是 MySQL 内部强一致；主要扩展风险是热门图片、热门作者的同步计数竞争，以及撤销热门作品时的大事务。

## 3. 最终目标架构

```text
前端乐观更新
    ↓
同一图片请求严格串行
    ↓
后端鉴权、限流
    ↓
Redis Lua 检查图片公开周期计数key并原子更新关系与计数
    ├─ 异步发布点赞状态事件到 RabbitMQ
    └─ 立即返回 204
            ↓
      like.events Exchange
        ├─ like.persistence.queue
        │    └─ 批量同步 MySQL 点赞关系和相关投影
        └─ like.notification.queue
             └─ 批量写通知记录，提交后批量发送 SSE

定时全量任务：Redis 当前关系和绝对计数 → 双向校正 MySQL
```

Redis 负责实时正确，MQ 负责低延迟传播，MySQL 负责持久查询，定时任务负责最终收敛。

## 4. 前端交互与请求顺序

### 4.1 已确认行为

- 前端乐观更新：点赞时在当前页面计数基础上 `+1`，取消时 `-1`。
- API 响应不返回 `likeCount`、`liked` 或 `changed`，继续使用 `204 No Content`。
- 接受多标签页、陈旧 DTO 等场景中的临时计数偏差；重新加载列表后以 Redis 当时快照校正。
- 前端不防抖、不合并用户操作，每一次点击都保留。
- 同一页面内，同一图片的请求必须严格串行：前一个请求收到响应后再发送下一个；不同图片可以并行。
- 前端在用户点击时立即生成 13 位毫秒 `timestamp`，而不是等请求真正出队发送时才生成；排队和重试必须复用该次点击的原 timestamp。
- 明确失败时回滚对应的乐观操作；结果未知的网络错误可用相同目标状态重试或重新读取状态校正。

“严格串行”不是按钮永久禁用，也不是把多次点击合并为一次。用户点击两次仍发送两次，只是保证发送次序与当前页面点击次序一致。

目标接口契约增加点击时间参数，但保持现有方法、路径和空响应：

```http
PUT /api/inspirations/{imageId}/like?publicationVersion={version}&timestamp={epochMillis}
DELETE /api/inspirations/{imageId}/like?publicationVersion={version}&timestamp={epochMillis}
```

`timestamp` 使用 `Date.now()` 产生的毫秒值，例如 `1787039748123`；不使用只能精确到秒的 `1787039748`。它表达用户点击时间，主要用于建立点赞关系时的列表排序，不承担 MQ/MySQL 的权威消息顺序。

### 4.2 多标签页和多设备

第一版不建立跨标签页、跨设备的全局点击顺序。跨客户端同时操作时，接受最后到达后端并被 Redis 接受的状态生效，页面刷新后以 Redis 为准。

## 5. Redis 数据模型和 Lua 规则

### 5.1 当前有效点赞关系

```text
likes:user:{userId}
  ZSET(
    member = imageId:publicationVersion,
    score  = likedAt
  )
```

该 ZSET 同时支持：

- 判断当前用户是否点赞某批图片；
- 按时间读取用户的当前有效点赞列表；
- 保存当前有效点赞关系的时间。

取消点赞直接 `ZREM`。由于已确认采用前端同图片串行和定时全量差集校正，Redis 不额外保存取消墓碑。代价是取消后 Redis 不再保留该关系的旧版本，因而不负责还原 Redis 之前发生的跨客户端请求乱序。

### 5.2 实时计数

```text
like:count:{imageId}:{publicationVersion}
  STRING(图片当前实时点赞数)
```

该 key 同时承担当前公开周期的“可点赞门闩”：

```text
key存在（包括value=0）
    → 该imageId:publicationVersion当前允许点赞

key不存在
    → 未公开、已撤销、版本失效，或Redis公开状态尚未初始化完成
    → PUT点赞失败
```

所有审核通过的公开图片必须创建对应 key，即使当前点赞数为 `0`；key 不设置 TTL，也不得被 Redis 淘汰策略自动删除。点赞接口不再为公开状态查询 MySQL，而由 Lua 以 key 是否存在完成门禁。

第一版不在 Redis 维护作者获赞总数。`users.received_like_count` 继续保存在 MySQL：普通点赞通过 MQ 批量更新，撤销发布在 MySQL 事务中同步扣减，定时任务再根据 Redis 中仍有效公开图片的绝对点赞数按作者汇总校正。这样撤销发布不需要立即修改 Redis 作者计数。

### 5.3 操作时间

- 点赞状态事件携带统一的服务端操作时间 `operationTime`。
- `likedAt` 是前端点击点赞时生成的毫秒 `timestamp`，表示真正发生“未点赞 → 已点赞”的用户操作时间，也是 Redis ZSET 的 score；重复点赞不得刷新它。
- `operationTime` 由服务端在真实状态变化时生成，只用于 MQ/MySQL 判断事件新旧。`like.created` 的 `likedAt` 与 `operationTime` 可以不同，二者不得混用。
- 当前单机前提下不再增加独立 `operationSequence`。
- `operationTime` 必须能够稳定比较；实现时使用服务端高精度时间，并保证连续真实状态变化不会得到无法区分的值。
- `publicationVersion` 必须进入 ZSET member、计数 key、MQ 消息和 MySQL 唯一键。

### 5.4 Lua 状态转换

Lua 首先检查 `like:count:{imageId}:{publicationVersion}` 是否存在，再原子完成关系与图片计数修改：

```text
PUT且计数key不存在
    → 返回PUBLICATION_UNAVAILABLE，不写用户ZSet、不发送MQ

DELETE且计数key不存在
    → 只ZREM当前用户可能残留的旧member，不递减不存在的计数，不发送MQ，按幂等成功返回204
```

计数 key 存在时，状态规则如下：

| Redis 当前状态 | 请求目标状态 | 关系处理 | 计数处理 | 事件 |
| --- | --- | --- | --- | --- |
| 未点赞 | 点赞 | `ZADD` 并写入新的 `likedAt` | 图片 `+1` | `like.created` |
| 已点赞 | 点赞 | 完全幂等，`likedAt` 和 score 不变 | 不变 | 不发送 |
| 已点赞 | 取消 | `ZREM` | 图片 `-1` | `like.removed` |
| 未点赞 | 取消 | 不变 | 不变 | 不发送 |

只有真正发生“未点赞 → 已点赞”时才更新 `likedAt` 和 ZSET score。这样与当前 MySQL `INSERT IGNORE` 行为一致，重复 `PUT` 不会把旧图片重新移动到用户点赞列表前部。

当 ZSET 中存在当前点赞关系时：

```text
目标仍为点赞
    → 直接按幂等成功处理，不修改score、计数，也不发送MQ

目标为取消
    → ZREM并递减计数，发布like.removed
```

当 ZSET 中不存在关系时，Redis 没有该关系最近一次取消时间，因而不能仅靠时间拒绝取消之后才到达的旧点赞。这一缺口由“当前页面同图片请求严格串行”和“跨客户端最后到达生效”的已确认规则承担，不再为此保存 Redis 取消记录。

Lua 的内部结果至少需要包含：

```text
stateChanged
previousLiked
currentLiked
```

这些字段只供后端选择消息类型。状态真实变化后由服务端生成 `operationTime` 并构造 MQ 事件；内部字段不进入 HTTP 响应。

`PUBLICATION_UNAVAILABLE` 应映射为项目统一的资源不可用错误，例如 `404 / GENERATION_RESOURCE_NOT_FOUND`，前端回滚乐观点赞并将陈旧详情切换为“作品已撤销或不可用”。

## 6. RabbitMQ 事件与路由

### 6.1 发布规则

Redis Lua 成功后立即返回 `204`；只有状态真实变化时，后端才异步发布对应的 `like.created` 或 `like.removed`：

```text
Redis成功
→ 异步尝试发布MQ
→ 不等待Publisher Confirm
→ 返回204
```

MQ 当场发送失败时记录日志、指标和告警，不回滚 Redis，也不要求前端回滚。点赞关系和计数由定时全量任务最终修复。

RabbitMQ 只承载点赞状态事件。作品审核通过和撤销发布不进入点赞 Exchange、不发送点赞 MQ，而是由发布服务在 MySQL 事务提交后直接创建或删除 Redis 计数门闩；失败由有限重试、告警和定时任务处理。

事件建议包含：

```json
{
  "eventId": "like:{userId}:{imageId}:{publicationVersion}:{operationTime}",
  "userId": 1001,
  "imageId": 2008,
  "publicationVersion": 3,
  "authorId": 3001,
  "liked": true,
  "likedAt": 1787030400123,
  "operationTime": 1787030400456789
}
```

`eventId` 用于 MySQL 通知和消费者幂等，不用于客户端生成顺序。

### 6.2 Exchange 和独立队列

不能让持久化消费者和通知消费者竞争消费同一个 Queue，否则一条消息只会被其中一个消费者获得。采用一个 Exchange、两个 Queue：

```text
Exchange: like.events

Routing keys:
- like.created
- like.removed

Queue: like.persistence.queue
- 绑定 created / removed

Queue: like.notification.queue
- 只绑定 created
```

队列可以继续使用 durable quorum queue 和持久化消息，但 HTTP 不等待发布确认。这样可以提高正常情况下的可靠性，同时不把 RabbitMQ 延迟耦合到点赞响应。

## 7. MySQL 点赞关系与计数投影

### 7.1 点赞关系状态表

异步消息可能重复和乱序，目标表需要保存最终状态，而不是取消即物理删除：

```text
user_image_like_states
- user_id
- image_id
- publication_version
- liked
- liked_at
- last_operation_time
PRIMARY KEY (user_id, image_id, publication_version)
```

字段语义：

- `liked`：MySQL 当前投影状态；
- `liked_at`：最近一次有效点赞时间，用于列表排序；
- `last_operation_time`：最近一次已处理点赞或取消事件时间，用于拒绝旧 MQ 消息。

消费者只接受：

```text
incoming.operationTime > stored.lastOperationTime
```

相同或更旧消息均忽略。判断与更新必须通过条件 Upsert 原子完成，不能先查询、在 Java 中比较、再无条件更新。

点赞持久化消费者不再查询 MySQL 图片发布状态。处理消息前只检查对应 Redis 计数门闩：

```text
like:count:{imageId}:{publicationVersion}存在
    → 按operationTime条件Upsert MySQL点赞关系

门闩不存在
    → 公开周期已经失效，不写关系，直接ACK
```

消费者检查门闩和写 MySQL 之间仍可能与撤销发布并发；这种极小窗口由定时全量校正清理，属于已接受的最终一致边界。

MySQL 的取消状态暂不物理删除，否则旧点赞消息在状态行消失后可能重新插入。Redis 不保存取消记录和 MySQL 保留 `liked=false` 状态并不矛盾：前者是实时当前集合，后者是异步投影的乱序防线。

### 7.2 计数

Redis 计数是事实值。MySQL 可以继续使用现有：

```text
generation_images.like_count
users.received_like_count
```

不强制新建单独计数表。MQ 消费可以让计数尽快更新，但最终校正必须读取 Redis 绝对计数并覆盖 MySQL，不能只依靠消息逐条 `+1/-1`。

消费者只有在关系条件更新实际生效且状态发生变化时才能增减 MySQL 临时投影，重复和旧消息不得重复修改计数。

## 8. 定时全量校正

### 8.1 校正方向

校正按数据领域分为两个有先后关系的方向：

```text
第一阶段：MySQL发布状态与publicationVersion → 校正Redis公开周期计数门闩
第二阶段：根据计数门闩清理用户ZSet中的失效member
第三阶段：Redis有效点赞关系与绝对计数 → 校正MySQL点赞投影
```

MySQL 不反向决定有效公开周期内“谁点赞了什么”和图片实时点赞数；Redis 也不独立决定图片是否公开。定时任务必须先根据 MySQL 恢复当前公开周期缺失的计数 key、删除已撤销或版本失效的计数 key，再清理用户关系并校正 MySQL，禁止顺序颠倒。当前公开周期的计数 key 异常缺失时，应先根据仍有效的 Redis 用户关系或持久化副本重建计数，不能直接把对应关系当作撤销数据删除。

当前撤销发布只把 `public_at` 设为空、把 `publication_review_status` 设为 `NONE`，不会立即增加 `publicationVersion`；版本在重新提交审核时才增加。因此清理条件不能只判断版本号更高，还必须判断：

```text
public_at为空
或publication_review_status不是APPROVED
或Redis member中的publicationVersion与MySQL当前版本不相等
```

命中任一条件，即删除该旧公开周期的 Redis 图片计数 key；随后扫描用户 ZSET 时，凡 member 对应计数 key 不存在即移除。对于 MySQL 当前仍公开且版本匹配的图片，则必须确保对应计数 key 存在。

### 8.2 点赞关系双向差集

由于 Redis 不保存取消记录，所谓“全量校正”必须同时扫描 Redis 当前有效关系和 MySQL 当前有效关系，计算完整差集：

```text
Redis有，MySQL没有或liked=false
    → MySQL设置liked=true并校正likedAt

Redis有，MySQL也有
    → 按Redis当前事实校正状态和时间

Redis没有，MySQL有且liked=true
    → MySQL设置liked=false
```

只扫描 Redis 并补充点赞不属于完整校正，因为无法发现已经从 Redis 消失的取消关系。

全量任务开始时生成服务端校正水位 `reconcileOperationTime`。本轮按 Redis 状态校正关系时，同时把 MySQL `last_operation_time` 至少推进到该水位。这样，本轮开始之前产生、但在校正完成后才到达的旧 MQ 消息不会再次覆盖校正结果；本轮开始之后产生的新事件具有更新的服务端 `operationTime`，仍可通过条件 Upsert 生效。校正水位只用于 MySQL 事件顺序，不得覆盖 Redis ZSET 中表示用户点击时间的 `likedAt`。

### 8.3 计数覆盖

```text
generation_images.like_count
    = Redis图片绝对点赞数

users.received_like_count
    = 按Redis中仍有效公开图片的绝对点赞数按作者汇总
```

### 8.4 已接受代价

- 全量差集的数据量和耗时会随点赞关系增长；第一版接受该成本，但从第一版起就必须分批处理，禁止一次把全部关系加载到 JVM 内存。Redis 使用 `SCAN/ZSCAN`，MySQL 使用主键游标分页，初始批次可配置为每批 `500～1000` 条。
- 对账过程中仍可能有新点赞写入，因此它不是严格的同一时刻快照；任务必须幂等，并允许下一轮继续收敛。
- Redis AOF 恢复点之后若丢失少量操作，MySQL 可能曾经收到这些操作；恢复后的全量任务仍以 Redis 为准，可能撤销 MySQL 中更晚但 Redis 已丢失的数据。这是已接受的数据损失边界。
- 定时任务至少记录最近成功时间、扫描数量、清理数量、差异数量、失败批次数和总耗时；只有实际规模证明全量分批扫描不可接受时，再增加反向索引或增量脏标记。

## 9. 通知与 SSE

### 9.1 通知语义

- 只有真实的“未点赞 → 已点赞”产生 `like.created` 通知事件。
- `like.removed` 不创建点赞通知。
- 自己点赞自己的作品不通知。
- 同一点赞者、图片、公开周期延续现有“最多通知一次”的语义；取消后再点赞不重复创建历史通知。
- 点赞事实不依赖通知是否成功，通知失败不得回滚 Redis。
- `like.created` 表示点赞被 Redis 门闩接受时真实发生过的历史事件。通知消费者不重新检查图片当前是否公开；即使作品随后撤销，通知仍按现有规则保留，读取时图片字段因版本失效返回 `null`。

### 9.2 不在点赞请求中写通知 Outbox

SSE 是在线推送，不要求在点赞 HTTP 请求中同步写 MySQL notification outbox。否则会重新把数据库写放回主链路，违背本次优化目标。

通知通过 `like.notification.queue` 异步消费。RabbitMQ 本身承担待消费缓冲，不另建应用内存 outbox 或 Redis Stream。

### 9.3 批量通知处理

通知消费者在内存中短暂凑批，但消息在处理完成前保持 RabbitMQ 未 ACK：

```text
最多等待1秒
或达到批量阈值（初始建议500条）
    ↓
按eventId和现有通知唯一语义去重
    ↓
批量插入MySQL通知记录
    ↓
事务提交
    ↓
只对本批实际新增通知按接收者分组发送SSE
    ↓
ACK本批MQ消息
```

具体批量阈值应配置化，`1 秒 / 500 条` 是初始值而非容量结论。它只影响通知入库和 SSE 的短暂延迟，不影响点赞接口响应。

数据库通知表应具有稳定唯一约束或 `event_id` 唯一键，重复投递不能产生重复通知。

### 9.4 SSE 失败处理

- MySQL 通知提交后再发送 SSE，不能先 SSE 再入库。
- 用户不在线、连接断开或发送失败时，不阻塞 MQ ACK，也不无限重试 SSE。
- 用户重新进入通知中心时从 MySQL 查询历史通知。
- 为保持现有前端契约和页面交互不变，第一版继续使用现有单条通知 SSE DTO；消费者只批量入库，提交后再逐条调用现有 SSE 推送能力，不改成通知数组协议。

### 9.5 已接受的通知缺口

RabbitMQ 发布本身允许极少量丢失，定时全量关系校正只能恢复当前点赞状态，不能重建所有已经消失的历史事件。例如用户点赞后立即取消且两条 MQ 都丢失，系统无法补建中间那条历史通知。当前方案接受这一点；如果未来要求每次通知事件绝对不丢，再引入可靠事件日志或 outbox。

## 10. 查询行为

- 图片列表和详情中的当前用户点赞状态从 Redis 批量读取，禁止逐图请求。
- 图片点赞数从 Redis 批量读取；前端本地乐观增减只是临时展示。
- 本人的点赞列表优先读取 Redis ZSET 候选，再由 MySQL 批量装配图片详情并校验公开状态和 `publicationVersion`。
- 他人的点赞列表是低频页面，可以读取最终一致的 MySQL，并继续应用隐私、公开状态和版本校验。

## 11. 限流与公开生命周期

### 11.1 限流

后端继续在执行 Redis Lua 前限流，目标至少包括：

- 用户全局点赞请求速率；
- 用户与单图片组合速率；
- IP 粗粒度速率。

IP 阈值必须考虑 NAT 下多个正常用户共享出口，不应作为唯一限制依据。

### 11.2 撤销发布和重新发布

`publicationVersion` 仍是必需边界。第一版已确认不增加“图片 → 用户”反向 SET，也不在撤销接口中遍历 Redis 用户 ZSET。

撤销发布同步事务继续负责：

```text
1. 锁定并校验作者图片
2. 将public_at设为空、publication_review_status设为NONE
3. 清空MySQL图片点赞数
4. 扣减MySQL作者获赞总数
5. 清理或失效MySQL当前公开周期点赞关系
6. 触发搜索投影移除
```

MySQL 撤销事务提交后，发布服务立即删除：

```text
DEL like:count:{imageId}:{publicationVersion}
```

撤销请求不遍历 Redis 用户 ZSET。计数 key 删除后，陈旧详情页继续发送 `PUT` 时，Lua 因门闩不存在直接返回作品不可用，不查询 MySQL、不写用户关系、不发送 MQ。用户 ZSET 中原有 member 由定时任务清理；陈旧页面发送 `DELETE` 时也可以顺手 `ZREM` 自己的残留 member，并按幂等成功处理。

审核通过新公开周期时，在 MySQL `APPROVED` 事务提交后创建：

```text
SET like:count:{imageId}:{publicationVersion} 0
```

旧页面携带旧 `publicationVersion`，对应计数 key 已不存在，因此不能操作新公开周期。创建失败时按“失败关闭”处理：图片可以暂时不可点赞，由有限重试、告警和定时任务补建，不能绕过 Redis 门闩直接写点赞。

发布审核通过和撤销发布均不进入 RabbitMQ：发布服务在各自 MySQL 事务提交后直接调用 Redis `SET/DEL`。Redis 调用失败时进行有限重试并记录告警，剩余不一致交给定时任务修复。

所有公开列表、图片详情和点赞列表装配仍以 MySQL 发布状态和当前版本过滤可见内容；点赞写接口本身不再逐次查询 MySQL，而只检查 Redis 计数门闩。

点赞持久化消费者不查询 MySQL 图片状态，只检查消息对应的 Redis 计数门闩。门闩不存在时直接 ACK 丢弃，不写 MySQL 点赞关系；门闩存在时按 `operationTime` 条件 Upsert。通知消费者不做这项当前状态检查，因为通知记录的是点赞发生时的历史事件，撤销发布不撤回既有点赞通知。

定时全量任务先按 MySQL 发布状态和版本校正 Redis 计数门闩，再扫描全部用户点赞 ZSET，删除对应门闩不存在的 member，最后进行 Redis → MySQL 点赞关系和计数校正。第一版接受全量扫描成本；只有实际数据规模证明扫描不可接受时，再增加反向索引。

MySQL 与 Redis 不能形成一个原子事务，因此仍存在已接受的小窗口：MySQL 撤销已经提交，但 Redis 计数 key 删除尚未完成或删除失败时，陈旧页面可能短暂点赞成功。删除操作需要立即有限重试并告警；计数门闩最终删除后，持久化消费者会丢弃尚未落库的旧周期消息，定时任务清理已经形成的短暂残留关系。

## 12. 搜索索引

Meilisearch 的点赞数允许最终一致。第一版继续以 MySQL 持久化投影作为搜索同步来源，避免让搜索索引直接依赖 Redis 运行状态。点赞持久化批次或全量校正更新 MySQL 后，再批量触发搜索投影更新；具体批量策略在实现阶段确定。

## 13. 参考文章评审结论

参考文章：[从零设计一个高并发点赞系统：缓存+MQ异步持久化实战](https://juejin.cn/post/7662951063265263643)。文章采用 Redis Lua、Kafka、MySQL 批量 Upsert 和定时校对，证明了总体方向是常见方案，但不能直接照搬：

- 文章声明的用户 ZSET 未在示例 Lua 中同步维护；
- 多 key Lua 与 Redis Cluster slot 设计不闭环；
- 异步 `send()` 不等于消息已可靠确认；
- MQ 状态消息缺少数据库条件版本更新；
- 批量消费前没有按同一关系压缩到最新状态；
- 文章用可能落后的 MySQL 反向覆盖 Redis，和 Redis 实时事实源定位冲突；
- 没有覆盖本项目的 `publicationVersion`、撤销发布、作者计数、通知唯一语义、隐私和搜索投影。

本项目吸收 Redis Lua、用户维度 ZSET、批量 MQ 消费、MySQL 条件 Upsert 和定时校正等思路，但以本文已确认的单机、最终一致边界为准。

## 14. 实施前剩余事项

核心架构已经确定，实施前仍需把以下细节落成：

1. 服务端 `operationTime`、全量校正水位的具体生成，以及同关系时间碰撞处理。
2. Redis Lua 的参数、公开周期计数门闩返回码、幂等 DELETE 和计数下限保护。
3. RabbitMQ Exchange、routing key、两个 quorum queue 的配置和消息 DTO。
4. MySQL 状态表迁移，以及现有 `generation_image_likes` 数据迁移方式。
5. 持久化消费者的 Redis 门闩批量检查、MySQL 条件 Upsert 和批次内同关系消息压缩规则。
6. 通知消费者不复查当前发布状态的历史事件语义，以及通知表唯一约束如何兼容“取消后再点赞不重复通知”。
7. 定时全量差集的频率、分页方式、批次大小、运行指标和人工触发入口。
8. Redis AOF/RDB、禁止淘汰、最大内存和启动恢复配置。
9. 在切换 Redis 为事实源之前，如何从现有 MySQL 点赞关系一次性初始化用户 ZSET，并为所有当前公开周期创建图片计数门闩；初始化期间必须避免新旧写链路同时改变数据。
10. 审核通过后创建门闩、撤销提交后删除门闩的失败重试与告警，以及全量任务“先校正门闩、再清用户关系、最后校正MySQL”的执行顺序。
11. 作者计数与 Meilisearch 的批量投影方式。

以上事项属于实现设计，不改变已经确认的总体结构。本文在实现和验收前继续保持独立，不提前合并到现有正式模块文档。
